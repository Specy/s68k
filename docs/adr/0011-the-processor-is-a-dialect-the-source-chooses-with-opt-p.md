# The processor is a dialect the source chooses with `opt p=`

s68k is EASy68K's 68000. A Program had no way to say it was written for a later processor, so the two instructions s68k already assembled from them, the 68010's `move ccr,<ea>` and the 68020's `extb.l`, were accepted in every program. That machine never existed: on a 68000 those words are illegal instructions, and EASy68K, real boards and exam environments refuse both. The asm-editor's design for a real 68000 behind the M68K Target (its `docs/design/m68k-machine.md`, decision 3, the spelling confirmed by the owner on 2026-10-28) makes the 68010 and the 68020 dialects a Program chooses, and its plan ships the plumbing with the 68000 work, so that the two instructions have a home from the day the 68000 refuses them (`docs/design/m68k-machine-plan.md`, planning decision 11, milestone C11). We decided four things.

- **The source chooses the processor, with `opt p=68000`, `opt p=68010` or `opt p=68020`.** It is the Devpac spelling, which vasm reads too, and it extends the `opt` EASy68K users already write; EASy68K's own `OPT BIT` keeps its meaning, the 68020's bit-field instructions on a 68000, and `p=68020` implies it (`docs/research/m68k-cpu-variants.md` §2.9 and §5 there).
    - **Once, before the first instruction**, a line whose Operation is a Mnemonic. Every instruction is judged and measured in pass 1 for the processor in force, so one chosen later would change what the lines above it are. Naming the same processor again is harmless; naming another is `processor_chosen_twice`, and an `opt p=` or `opt bit` after the first instruction is `processor_chosen_after_code`, which chooses nothing. GNU `as` has the same rule for `.arch` and `.cpu`.
    - A value that is not one of the three is `unknown_processor`, naming them. The words are read case insensitively, as EASy68K reads them. EASy68K's listing options (`cre`, `mex`, `sex`, `war`, `cex` and their `no` forms) are accepted and change nothing, and any other word is the warning `unknown_option`, so that a misspelt `p=` is not a program left on the 68000 in silence.
    - The Program carries the result, `Program::processor` and `Program::bit_fields` (`processor` and `bitFields` of `getInfo()`), as it carries the memory map: it travels with the source, a Playground and an exam, and the editor only displays it. A per-Program Setting was the alternative, as the RISC-V assembly profile is one; the processor decides whether the source assembles at all, so it belongs in the source.
- **One machine with gates.** There is one table, one decoder, one encoder, one executor and one disassembler. Each Form of the instruction table names the first processor that has it, as each row of the decoder already did, and the analyzer refuses a Form above the Program's processor; the forms export says it per form (`processor`). The Interpreter decodes memory for the Program's processor, on a miss of the decode cache and in `disassemble_at`, so a word of a later processor is an illegal instruction in an earlier one's Program, there as in its disassembly.
    - A branch written `.l` is a word on the 68000 and the 68010, which have no long branch, as in EASy68K, and the 68020's long branch, `$xxFF` and a 32-bit displacement, under `opt p=68020`. An unsized branch is chosen as before on every processor.
- **`move ccr,<ea>` and `extb.l` are the first members**, the 68010's and the 68020's. In a Program for an earlier processor each is `needs_a_later_processor`, whose hint has two halves: the 68000's way of doing the same (`ext.w` then `ext.l`; `move sr,<ea>`, whose low byte is the CCR) and the `opt p=` line that writes the program for the processor. The Diagnostic carries both as **suggested fixes**, the `opt p=` line first, which the editor offers as quick fixes, so a saved program migrates in one click. A fix is the smallest edit an editor can apply blind: a title, a Location and the text that replaces what it covers, where a Location with no columns inserts. The `opt p=` fix changes the value of the line that chose the processor when there is one, wherever it is in the Project, and otherwise adds a line above the first line of the Entry file that is not blank or a Comment line, which comes before every instruction.
- **The rest of each dialect arrives in its own batch, and says so until then.** Every other instruction of the 68010 and the 68020 is a row of the table marked not implemented yet, and the shapes the 68020 gives a 68000 Mnemonic (`muls.l`, `divs.l`, `chk.l`, `link.l`, `tst` of an address register, a PC-relative operand or an immediate, `cmpi` against the program counter) are listed beside it. The instructions are `unimplemented_in_dialect` in every Program, since no `opt p=` would make them assemble, and their lines are read as raw text, so the bit fields' `{4:8}` raises nothing else. The shapes are `unimplemented_in_dialect` in a Program for their processor, and judged as the 68000 judges them, an invalid size or addressing mode, in an earlier one. `callm` and `rtm` are left out for good, as `unimplemented_operation`.

## Considered options

- **Keeping `move ccr,<ea>` and `extb.l` in 68000 Programs**, as lenient extensions in the spirit of ADR 0001: possible, since the reference suite tests none of the 58 opcode words that would decode differently from a 68000, but the machine would be one that never existed, and a program written for it fails in EASy68K and on every board (`docs/research/m68k-cpu-variants.md` §6.4 there).
- **A per-Program Setting** for the processor: the editor would have to carry it beside the source into every Playground, exam and download, and a source read without it would mean something else.
- **`machine 68020`, `mc68020` or `.cpu 68020`**, vasm's and GNU's spellings: a directive EASy68K users have never seen, or a dotted style EASy68K does not use.
- **`opt bit` anywhere**, as EASy68K takes it: EASy68K's simulator reads the option from the listing for the whole program, so its position never mattered there, but here the instructions above it would have been judged without it. It is chosen before the first instruction, with the processor; a program that writes it at the top, as EASy68K's examples do, is unaffected.
- **Refusing unknown `opt` words**, as EASy68K's syntax error does: they change nothing either way, so a warning says what matters without failing a build ported from another assembler.

## Consequences

- ADR 0001 gains one strictness: `opt bit` after the first instruction, which EASy68K accepts, is an error here. EASy68K's `OPT P=68020`, which is a syntax error there, is accepted here, as every 68010 and 68020 instruction already was an error there.
- A Program that used `move ccr,<ea>` or `extb.l` without `opt p=` no longer assembles; the Diagnostic's first fix adds the line that makes it assemble as before.
- `Diagnostic` carries `fixes`, serialised only when there are some, so every other Diagnostic crosses into TypeScript as it did. A suggested fix is a type of its own, `SuggestedFix`, in Rust and in TypeScript.
- The table rows of the later instructions are Mnemonics, so a word in column 1 such as `pack` or `cas` is read as the Operation, as `clr` is (`docs/grammar.md` 3.2), and is offered the colon; none of the corpus programs writes one. They are not offered as a "did you mean", which would only lead to another error.
- The S-record of a non-68000 Program does not run in EASy68K, except bit fields under `opt bit`, and the editor says so at the Build (the plan's E5).
- Batches 4 and 5 of the plan fill the dialects in: each instruction that lands leaves the not-implemented list, gains its Forms with their processor, and is read as Operands again. The decoder's processor-dependent readings, the index extension word and the frames, the vector base and the timing, go with them.
