# The processor is a dialect the source chooses with `opt p=`

s68k is EASy68K's 68000. A Program had no way to say it was written for a later processor, so the two instructions s68k already assembled from them, the 68010's `move ccr,<ea>` and the 68020's `extb.l`, were accepted in every program. That machine never existed: on a 68000 those words are illegal instructions, and EASy68K, real boards and exam environments refuse both. The asm-editor's design for a real 68000 behind the M68K Target (its `docs/design/m68k-machine.md`, decision 3, the spelling confirmed by the owner on 2026-10-28) makes the 68010 and the 68020 dialects a Program chooses, and its plan ships the plumbing with the 68000 work, so that the two instructions have a home from the day the 68000 refuses them (`docs/design/m68k-machine-plan.md`, planning decision 11, milestone C11). We decided four things.

- **The source chooses the processor, with `opt p=68000`, `opt p=68010` or `opt p=68020`.** It is the Devpac spelling, which vasm reads too, and it extends the `opt` EASy68K users already write; EASy68K's own `OPT BIT` keeps its meaning, the 68020's bit-field instructions on a 68000, and `p=68020` implies it (`docs/research/m68k-cpu-variants.md` §2.9 and §5 there).
    - **Once, before the first instruction**, a line whose Operation is a Mnemonic. Every instruction is judged and measured in pass 1 for the processor in force, so one chosen later would change what the lines above it are. Naming the same processor again is harmless; naming another is `processor_chosen_twice`, and an `opt p=` or `opt bit` after the first instruction is `processor_chosen_after_code`, which chooses nothing. GNU `as` has the same rule for `.arch` and `.cpu`.
    - A value that is not one of the three is `unknown_processor`, naming them. The words are read case insensitively, as EASy68K reads them. EASy68K's listing options (`cre`, `mex`, `sex`, `war`, `cex` and their `no` forms) are accepted and change nothing, and any other word is the warning `unknown_option`, so that a misspelt `p=` is not a program left on the 68000 in silence.
    - The Program carries the result, `Program::processor` and `Program::bit_fields` (`processor` and `bitFields` of `getInfo()`), as it carries the memory map: it travels with the source, a Playground and an exam, and the editor only displays it. A per-Program Setting was the alternative, as the RISC-V assembly profile is one; the processor decides whether the source assembles at all, so it belongs in the source.
- **One machine with gates.** There is one table, one decoder, one encoder, one executor and one disassembler. Each Form of the instruction table names the first processor that has it, as each row of the decoder already did, and the analyzer refuses a Form above the Program's processor; the forms export says it per form (`processor`). The Interpreter decodes memory for the Program's processor, on a miss of the decode cache and in `disassemble_at`, so a word of a later processor is an illegal instruction in an earlier one's Program, there as in its disassembly.
    - A branch written `.l` is a word on the 68000 and the 68010, which have no long branch, as in EASy68K, and the 68020's long branch, `$xxFF` and a 32-bit displacement, under `opt p=68020`. An unsized branch is chosen as before on every processor.
- **`move ccr,<ea>` and `extb.l` are the first members**, the 68010's and the 68020's. In a Program for an earlier processor each is `needs_a_later_processor`, whose hint has two halves: the 68000's way of doing the same (`ext.w` then `ext.l`; `move sr,<ea>`, whose low byte is the CCR) and the `opt p=` line that writes the program for the processor. The Diagnostic carries both as **suggested fixes**, the `opt p=` line first, which the editor offers as quick fixes, so a saved program migrates in one click. A fix is the smallest edit an editor can apply blind: a title, a Location and the text that replaces what it covers, where a Location with no columns inserts. The `opt p=` fix changes the value of the line that chose the processor when there is one, wherever it is in the Project, and otherwise adds a line above the first line of the Entry file that is not blank or a Comment line, which comes before every instruction.
- **The rest of each dialect arrives in its own batch, and says so until then.** *(Amended on 2026-10-29 with milestone C12: the 68010 is complete, and only the 68020 says so; see the amendment at the end.)* Every other instruction of the 68010 and the 68020 is a row of the table marked not implemented yet, and the shapes the 68020 gives a 68000 Mnemonic (`muls.l`, `divs.l`, `chk.l`, `link.l`, `tst` of an address register, a PC-relative operand or an immediate, `cmpi` against the program counter) are listed beside it. The instructions are `unimplemented_in_dialect` in every Program, since no `opt p=` would make them assemble, and their lines are read as raw text, so the bit fields' `{4:8}` raises nothing else. The shapes are `unimplemented_in_dialect` in a Program for their processor, and judged as the 68000 judges them, an invalid size or addressing mode, in an earlier one. `callm` and `rtm` are left out for good, as `unimplemented_operation`.

## Considered options

- **Keeping `move ccr,<ea>` and `extb.l` in 68000 Programs**, as lenient extensions in the spirit of ADR 0001: possible, since the reference suite tests none of the 58 opcode words that would decode differently from a 68000, but the machine would be one that never existed, and a program written for it fails in EASy68K and on every board (`docs/research/m68k-cpu-variants.md` §6.4 there).
- **A per-Program Setting** for the processor: the editor would have to carry it beside the source into every Playground, exam and download, and a source read without it would mean something else.
- **`machine 68020`, `mc68020` or `.cpu 68020`**, vasm's and GNU's spellings: a directive EASy68K users have never seen, or a dotted style EASy68K does not use.
- **`opt bit` anywhere**, as EASy68K takes it: EASy68K's simulator reads the option from the listing for the whole program, so its position never mattered there, but here the instructions above it would have been judged without it. It is chosen before the first instruction, with the processor; a program that writes it at the top, as EASy68K's examples do, is unaffected.
- **Refusing unknown `opt` words**, as EASy68K's syntax error does: they change nothing either way, so a warning says what matters without failing a build ported from another assembler.

## Consequences

- ADR 0001 gains one strictness: `opt bit` after the first instruction, which EASy68K accepts, is an error here. EASy68K's `OPT P=68020`, which is a syntax error there, is accepted here, as every 68010 and 68020 instruction already was an error there.
- A Program that used `move ccr,<ea>` or `extb.l` without `opt p=` no longer assembles; the Diagnostic's first fix adds the line that makes it assemble as before.
- `Diagnostic` carries `fixes`, serialised only when there are some, so every other Diagnostic crosses into TypeScript as it did. A suggested fix is a type of its own, `SuggestedFix`, in Rust and in TypeScript.
- The table rows of the later instructions are Mnemonics, so a word in column 1 such as `pack` or `cas` is read as the Operation, as `clr` is (`docs/grammar.md` 3.2), and is offered the colon; none of the corpus programs writes one. They are not offered as a "did you mean", which would only lead to another error.
- The S-record of a non-68000 Program does not run in EASy68K, except bit fields under `opt bit`, and the editor says so at the Build (the plan's E5).
- Batches 4 and 5 of the plan fill the dialects in: each instruction that lands leaves the not-implemented list, gains its Forms with their processor, and is read as Operands again. The decoder's processor-dependent readings, the index extension word and the frames, the vector base and the timing, go with them.

## Amendment, 2026-10-29: the 68010 is complete (milestone C12)

The 68010 is no longer partial. Under `opt p=68010` a Program has the whole of the design's decision 3 for it:

- **Its instructions**: `move ccr,<ea>`, `rtd`, `bkpt`, which takes the illegal instruction exception as a 68010 does when nothing answers its breakpoint cycle, `movec` with SFC, DFC, USP and VBR, an unknown control register being an illegal instruction, and `moves`; `movec` and `moves` are privileged, and so is `move sr,<ea>` from the 68010 on. A Form now says the first processor that runs it only in supervisor mode (`privilegedFrom` in the forms export), as it says the first that has it. `sfc`, `dfc` and `vbr` are Operands of their own and reserved names in every Program, as `usp` is: a 68000 Program that called a Symbol so is told to rename it, a strictness ADR 0001 records, so that a name means one thing in every dialect.
- **Function codes.** s68k has one address space, so SFC and DFC are three bits each that `movec` writes and reads, and `moves` reaches the memory `move` does, as a supervisor data access. Nothing else reads them.
- **The VBR and the frames.** Every Exception reads its Vector through the VBR and pushes the 68010's frame: format `$0`, eight bytes, and for the bus and address errors format `$8`, 29 words, whose three buffers and sixteen internal words, its version among them, are written as zeros, and whose program counter is that of the instruction that faulted. `rte` reads the format first; format `$8` returns to the stacked program counter, so the instruction runs again from its start, restarted rather than continued, as Musashi does; any other format, or a version that is not 0, is the format error, vector 14, with the flags a 68010 sets.
- **Cycles and loop mode.** The 68010 counts its own Cycles, with Loop mode, which changes Cycles only. The values are the manual's section 9 where it is exact, and Moira's 68010 where it gives a maximum or departs from it, since Moira counts its cycles access by access and is checked against cputester on the hardware.
- **Verification.** No suite covers the 68010, so it is checked by a differential harness behind two opt-in features, `musashi` and `moira`, each building its reference with the `cc` crate from a copy a script fetches, never at a default build: Musashi for behaviour, every 68010 instruction from random states with its frames and trace, where it is not the 68010 listed with reasons; and Moira for behaviour and Cycles, every instruction and every one-instruction loop step by step. GNU `as -m68010` checks the encodings.

Until the 68020's batch, a Program for the 68020 runs as a 68010, its frames, VBR and Cycles included, without Loop mode, which the 68020 does not have.

## Amendment, 2026-10-29: the 68020's addressing modes and long branches (milestone C13a)

The 68020 has its addressing modes. Under `opt p=68020` every position that takes `d8(An,Xn)` or `d8(PC,Xn)` takes all of them, since they are encoded in the same two modes: the scaled index of the brief extension word, and the full extension word with a base displacement of a word or a long, the base and the index each suppressed or left out, and memory indirection, preindexed and postindexed, with an outer displacement (M68020UM, and the M68000 Programmer's Reference Manual 2.2.7 to 2.2.15). We decided four more things.

- **The syntax is vasm's and GNU `as`'s in Motorola mode**, `(bd,An,Xn.SIZE*SCALE)`, `([bd,An],Xn,od)` and `([bd,An,Xn],od)`, each part left out at will, `za0`–`za7`, `zd0`–`zd7` and `zpc` for a suppressed register, and `.w` or `.l` after a displacement for its width. The suppressed registers are registers only inside the parentheses, as `pc` is, and are not reserved, so that no 68000 Program loses a name to them. An index register with no size is `.w`, as on the 68000 and in EASy68K, where GNU `as` makes it a long. `(d0)`, the 68020's data register indirect, is `needs_a_later_processor` in an earlier Program, whose hint gives the 68000's way, an address register the data register is copied into (`movea.w d3,a3` and `(a3)` for `(d3)`, amended with C13c); the forms the 68000 already refused as a base that is not an address register, `4(d0)` and `(d0,d1)`, keep their `malformed_operand`.
- **The widths follow EASy68K's back-reference rule, extended where the 68000 has no encoding.** A line the 68000 encodes keeps the 68000's encoding under `opt p=68020`, so adding the line changes no instruction that assembled without it. A displacement above the line that the 68000's field does not hold, `d(An)` and `d(PC)` past a word or `d(An,Xn)` and `d(PC,Xn)` past a byte, is the 68020's base displacement, a word or a long as it needs, and an unsized branch back further than a word reaches is `.l`, as vasm makes it. A name below the line keeps the 68000's field and is an error when it does not fit, whose hint is to write the width: with no relaxation, a forward branch that may be long would be long every time, and EASy68K's rule gives a Forward reference the largest form only where that form is not a cost to every line. In the 68020's own forms, which the 68000 has no encoding for, a displacement with no width follows the rule of an absolute address: none for a known 0, a word or a long for a known value, a long for a name below.
- **One Operand of the encoded instruction carries them**, `Operand::Extended`: the base register, the extension word as encoded, read through `ExtensionWord`, and the two displacements, in the twelve bytes the 68000's Operands take in WebAssembly, so that no instruction in the decode cache grows. The decoder makes one only for the 68020 and only for a word whose bits 10–8 are not clear, so a word the 68000 reads means the same on every processor; the reserved combinations are read bit by bit, as Musashi reads them, and print as their words. Everything the 68020 adds runs off the paths of the 68000's modes: its reads and writes are cold functions, and a memory indirect Operand that is read and written back works its address out twice, which finds the same pointer, as nothing is written between the two.
- **Cycles are a placeholder.** The 68020 counts as a 68010, and its own modes take the time of `d8(An,Xn)`, marked as such in `machine::timing`, until the cache-case estimate of the 68020's cycles. *(Replaced with milestone C13d: see the last amendment.)*

GNU `as -m68020` writes the same words for every form, and the differential harness runs random Operands of every mode beside Musashi's 68EC020, which models all of them. Until the rest of the 68020's batch, an operand or a pointer at an odd address is an address error, as on the 68000, and a step keeps ten bytes of the instruction it ran, so one longer, decoded from memory, says nothing of what ran.

## Amendment, 2026-10-29: the 68020's instructions (milestone C13b)

Under `opt p=68020` a Program has every integer instruction of the 68020 a user-mode program runs: `chk.l`, `link.l`, the 68020's `tst` of an address register, a PC-relative operand or an immediate and its `cmpi` against the program counter, every `trapcc` of no operand, a word or a long, `muls.l` and `mulu.l` into `Dl` or `Dh:Dl`, `divs.l`, `divu.l`, `divsl.l` and `divul.l`, `pack` and `unpk`, `chk2` and `cmp2`, `cas` and `cas2`, and the eight bit-field instructions. `callm` and `rtm` stay refused for good. We decided five more things.

- **The shapes the 68020 gave a 68000 Mnemonic are Forms of their own**, with the 68020 as their processor: `chk.l` beside `chk`, `link.l` beside `link`, the long `muls` and `divs` beside the word ones, the 68020's `tst` and `cmpi` beside the 68000's. A written size decides between two Forms the Operands both fit, so `chk.l d0,d1` is the 68020's and `chk d0,d1` the 68000's, and a 68000 Program is told `` `chk.l d0,d1` is a 68020 instruction ``, with the `opt p=` fix, where it was told of a size or an addressing mode it does not have. With nothing still to come, `unimplemented_in_dialect`, the rows it answered and the raw reading of their lines are gone.
- **Three new shapes of Operand**, each a mode of the table: a register pair, `d1:d2`, for `Dh:Dl`, `Dr:Dq` and `cas2`'s compare and update registers; `cas2`'s indirect pair, `(a0):(d1)`; and a bit field, `{offset:width}` straight after its Operand, each half a number, with a `#` as GNU `as` reads it or without, or a data register. The Operand with a field is of its own mode and the field's, so only the bit-field instructions take one, and they take nothing without one. `{` and `}` are tokens, and count as parentheses where whitespace would end the Operand field.
- **`opt bit` gives a 68000 or 68010 Program the bit fields**, as EASy68K's option does, with that processor's addressing modes, so `(8,a0,d1.w*4){0:8}` still needs `opt p=68020`. The decoder reads a `Dialect`, a processor and whether it has the bit fields, which a processor alone gives the 68020 only; the Program says its own (`Program::dialect`). A bit field in an earlier Program without `opt bit` is `needs_a_later_processor`, whose second fix writes `opt bit`, or `,bit` after the value of the `opt p=` line.
- **Where Motorola leaves a flag or a result undefined, s68k is the 68020 as WinUAE has it from Toni Wilen's cputester runs on the hardware**: `chk`'s and `chk.l`'s V and C out of bounds, `chk2`'s N and V, N and Z after a long division that overflows or divides by zero, the high half of a product into `Dh:Dh`, and `pack`'s and `unpk`'s byte order. The manual decides the rest, as the 68000's suite decides the 68000. `chk2` compares signed when the lower bound is not above the upper and as the unsigned range that wraps round otherwise; `cas2` with one register for both compare values keeps the first operand, as the manual says; `bfffo` answers the offset as written, a register's whole, plus how far in the first set bit is. Musashi, which models the 68040 in several of these and errs in others, is compared outside them, its gaps listed in the harness.
- **`cas` and `cas2` are one step**, which nothing can come between: s68k has one processor and no bus to lock, so a locked read-modify-write and an ordinary one are the same.

Their cycles are a placeholder, the time of the 68000 instruction nearest each, marked as such in `machine::timing`, until the 68020's cache-case estimate *(replaced with milestone C13d: see the last amendment)*; the bit fields take EASy68K's, the 68020's cache case and the 68000's effective address time, which is what EASy68K counts under `opt bit` and so the reference for a 68000 Program. GNU `as -m68020` writes the same words for every Form; Musashi's 68EC020 runs every new first word alike from random states, outside its listed gaps and the cases that take an exception, whose frames are still the 68010's; Musashi and the decoder agree on which first words are instructions; and seventeen of Musashi's mc68040 self-checking programs, vendored, run as 68020 Programs and pass, with their checks of the 68040's own readings relaxed and named. The 68020's supervisor model, its unaligned data, frames, stack pointers and cycles are the rest of its batch.

## Amendment, 2026-10-29: the 68020's supervisor model (milestone C13c)

Under `opt p=68020` a Program has the supervisor model of the 68EC020 the design's decision 3 scopes, and the 68020 dialect is complete but for its Cycles. We decided five more things.

- **The status register has T1, T0 and M**, the implemented bits `$F71F`; the 68000 and the 68010 keep `$A71F`. T1 is the 68000's T. T0, with T1 clear, traces an instruction that changed the flow of the program, as M68020UM 6.3.9 has it, and as WinUAE's 68020, which cputester checks, draws its line: a branch taken, `bra` and `bsr`, a jump, a return, and a write of SR, or of CCR by `andi`, `ori` or `eori`. An instruction that raised an exception is not traced by T0, which taking the exception clears, nor `stop`, which stops. Musashi also traces `nop`, `movec`, `moves`, `move` to USP, `stop`, `cas` and `cas2`, which is the 68040, and is compared outside them. A step still tests T1 and T0 with one comparison of the status register's high byte, whose two high bits they are, so a 68000 step pays nothing for T0.
- **Three stack pointers, and `ssp` keeps its meaning.** A7 is the USP in user mode, and in supervisor mode the ISP while M is clear and the MSP while it is set. The ISP is the SSP of the 68000 and the 68010, and `ssp` names it everywhere it did, in the System register file, in `setSsp` and in the journal's `WriteStackPointers`, which gains `msp`, 0 before the 68020; the System file of a 68020 adds `isp`, the same register under its 68020 name, `msp`, `cacr` and `caar`. The alternative, an `ssp` that read the supervisor stack pointer M selects, would have made a journal entry mean different registers in different modes. Every swap and every write of a stack pointer journals all three, and each keeps its own stack top. An IRQ taken with M set pushes its frame on the MSP, clears M and pushes the throwaway frame, format `$1`, on the ISP, with the status register it interrupted with S set, as Musashi and WinUAE push it and as M68020UM 6.3.11 needs for `rte` to find S and M in it and go back to the MSP.
- **`movec` reaches MSP, ISP, CACR and CAAR**, and `msp`, `isp`, `cacr` and `caar` are Operands of their own and reserved names in every Program, as the 68010's are; an earlier Program that names one is `needs_a_later_processor`, about a control register. CACR keeps E and F: C and CE are commands to a cache that read as 0 (M68020UM 7.1.2), and s68k has no cache, so E changes nothing and code a program writes runs as written. CAAR keeps every bit.
- **The frames are the 68020's, the bus fault frames simplified as the 68010's `$8` is.** Format `$0` for an IRQ, `trap #n`, an illegal instruction, line A and F, a privilege violation and the format error; format `$2`, which adds the instruction's address, for `chk`, `chk2`, `trapcc`, `trapv`, a division by zero and trace (M68020UM 6.3.4 and 6.5.3). A bus or an address error pushes the long bus fault frame, `$B`, the instruction it stacks being the one in execution, but a bus error on the fetch of an instruction none of which ran, at an instruction boundary, pushes the short one, `$A`, the instruction it stacks being the next to run (M68020UM 6.3.3 and 6.5.5); the address error of an odd program counter is `$B`, as WinUAE's 68020 pushes it. The special status word and the data cycle fault address are real, the internal words zeros, the version of `$B` 0, and `rte` restarts the instruction at the stacked program counter. `rte` takes `$0`, `$1`, `$2`, `$A` and `$B`, checks `$B`'s version, and raises the format error on any other, the 68010's `$8` among them, leaving the flags as WinUAE's 68020 does. Line F with no coprocessor is vector 11, as M68020UM 6.3.7 has it when no coprocessor answers.
- **Data at odd addresses is read and written**, as M68020UM 2.3 says, on every path into memory, and only an instruction fetched from an odd address is an address error. The odd address's check asks for the processor only once it finds one, inside the branch it already took, so an even access costs a 68000 Program what it did.

The `(dN)` refusal's hint names the register written: copy it into an address register, `movea.w d3,a3`, and write `(a3)`, `movea.l` for a long index and a6 for d7. No fix writes it, as only the student knows which address register is free.

Cycles stay a placeholder: the 68020's exceptions take the 68010's times, marked as such in `machine::timing`, until the cache-case estimate *(replaced with milestone C13d: see the next amendment)*. Musashi's 68EC020, which models the 68020's frames, M and the three stack pointers, checks it beside the hand tests: the 68010's instructions on the 68020 and the 68020's own from states with T1, T0, S and M random and a master stack of their own, interrupts in either state with their throwaway frames, and `rte` of the frames both pop, outside its listed gaps, which are the 68040's tracing under T0, no address error, its FPU's line F words, its format error on the bus fault frames, CACR's command bits, and the flags the 68020 leaves undefined. With this the 68020's batch is complete but for its cycles.

## Amendment, 2026-10-29: the 68020's cycles (milestone C13d)

A Program for the 68020 counts its own Cycles, and the 68020 dialect is complete. No exact count exists to copy: the timing tables of M68020UM (section 8 of the 1995 edition, 9 of the 1984 one) give each row a best case, a cache case and a worst case, and say that the real time depends on the instruction cache, the prefetch and how neighbouring instructions overlap, which no table can anticipate. We decided four things.

- **The counter is the cache case, and says it is an estimate.** The cache case is the instruction in the cache with no overlap: deterministic, so undo, Testcases and tasks 30 and 31 stay reproducible; the middle of the three; the column Musashi's 68020 keeps, so it can be cross-checked; and what EASy68K's bit fields already count (`docs/research/m68k-cpu-variants.md` §3.4 in the asm-editor). A model of the cache and the overlap, as Moira's and WinUAE's are, needs a bus and a prefetch s68k does not have, and the worst case is the time of cache-disabled code only. The Program says which kind its counter is, `Processor::cycles_exact` and `cyclesExact` in `getInfo()` (`hasExactCycles()` in TypeScript): true for the 68000 and the 68010, false for the 68020, which the editor marks as an estimate (the design's decision 30). A 68000 or a 68010 Program under `opt bit` that has a bit-field instruction says false too, `Program::cycles_exact`: its bit fields take EASy68K's time, the 68020's cache case for the field, which no 68000 or 68010 has, so its count is exact for every other instruction and an estimate as a whole.
- **The manual's tables compose as its notes say.** An instruction's time is its operation's and the fetch, calculate, immediate or jump effective address time of its operand, an extension word counting as an immediate word; `move` has its own table, which is two cycles, the source's fetch and a destination's time that depends on whether the source is a register, an immediate or memory, every one of its cells checked. Each Operand is a row of the tables: the 68000's modes, an immediate by its size, the brief extension word, and the full one's twelve, by the widths of its displacements and whether it reads memory. The data counts only where the manual's times depend on it, through each processor's `Extras` and `rte`'s frame format: a shift by any count, a multiply and a division by any operand, and a bit of a register above 15 take one time. The time is still decided when the decode cache keeps an instruction, and the 68000's and the 68010's immediate shift counts now are too, so a step pays at run time only for a count a register holds and the 68000's throughput does not drop.
- **Where the manual gives no time, or two, s68k chooses, and `machine::timing` says so.** `chk`, `chk2` and a division by zero take `trapv`'s trap time and their source's effective address, as on the 68000 they take their trap's time and theirs; `bkpt` its breakpoint cycle and the illegal instruction's time; the format error `rte`'s and an exception's; a bus or an address error the time of the frame it pushes alone; `nbcd` of memory Musashi's time. A full extension word with a word displacement takes the `(d16,B)` row, as Musashi does, and not the `(d16,An,Xn)` row, whose times are lower for the same word; the rows the manual leaves out, `-(An)` of the calculate immediate table and `([d16,B],I,d32)` of the fetch immediate one, take their neighbours'. Operands are taken as aligned, as the tables assume.
- **Musashi is reported, not asserted.** Its 68020 keeps the cache case, one number per opcode and a table per mode, but adds its fetch time where the manual adds the calculate or jump time, leaves out extension words and immediates, adds both of `move`'s effective addresses, charges a rotate per bit, and keeps the 68000's times for some exceptions. The harness counts the cases that agree and tallies the rest by instruction, as it does for the 68010's maxima; the unit tests check s68k against the manual itself.

## Amendment, 2026-10-30: the assembly says the processor, error or not

The asm-editor's documentation panel and completion follow the processor a Program chooses, and hide what a later one brought (its `docs/design/m68k-machine.md`, decision 36, the owner's call on 2026-10-30). The editor checks a source as it is typed, so more often than not the source has an error and there is no Program to ask. The assembly now says the dialect itself, `Assembly::dialect` (`processor` and `bitFields` of `AssemblyResult` in TypeScript), whether or not it built a Program: what the `opt p=` and `opt bit` lines before the first instruction chose, which the Layout has decided by the end of pass 1 whatever pass 2 finds, and the 68000 without the bit fields when no line chose or there was no Entry file to read. It is the Program's own `Program::dialect` when there is one, so the two cannot differ, and `getInfo()` keeps its `processor` and `bitFields` for a host that holds a Program.
