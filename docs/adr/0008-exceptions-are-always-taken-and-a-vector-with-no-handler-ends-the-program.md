# Exceptions are always taken, and a vector with no handler ends the program

Every runtime error ended the program: a 68000 would push a frame and jump through a vector, and s68k had neither, so a division by zero, `chk`, `trapv`, `illegal`, an address error and an unknown `trap #15` task all stopped the run, and `trap #0` to `#14`, `rte` and `move usp` were refused by the Assembler. EASy68K has the machinery behind an option, "Enable exceptions", which is off by default; with it off, every exception halts its simulator as s68k did. The asm-editor's design for a real 68000 behind the M68K Target (its `docs/design/m68k-machine.md`, decisions 9 to 12, decision 9 confirmed by the owner) asked for exceptions as a 68000 takes them, without losing what a program that installs no handler did. We decided four things.

- **Every exception is taken.** An instruction that raises one pushes a frame on the supervisor stack and jumps through its vector, whatever the program asked for: there is no option, and task 32 with 5 in D1.B, EASy68K's way of turning the option on, is accepted and changes nothing. The exceptions are those EASy68K has: the address error (3), an illegal instruction (4, `illegal` and a word that is no instruction), a division by zero (5), `chk` (6), `trapv` (7), a privilege violation (8), trace (9), the line A and line F words (10, 11), `trap #0` to `#14` (32 to 46) and a `trap #15` task EASy68K does not know (47). The bus error (2) comes with the memory map (the plan's milestone C7), and the interrupts with `stop` and `reset` (C8). *(Amended on 2026-10-28 with milestone C7: the bus error is taken, through vector 2, for every access the memory map refuses, an instruction's fetch and a `trap #15` task's buffer included.)* Spurious, uninitialised and vectored interrupts, which EASy68K lacks, are left out.
- **A vector holding an odd address has no handler, and the program ends as it did before.** On a 68000 the jump would raise an address error on the handler's fetch, then another on that one's vector, and the processor would halt. Instead the vector is read first, and an odd one ends the program with the first exception as its cause, the registers and the stack as the instruction left them, and the vector named beside the cause: `Termination::Exception { cause, vector }`, from which the editor can word "Division by zero at line 12: vector 5 at $000014 holds no handler". Memory starts as `$FF`, so every vector holds `$FFFFFFFF` until the program writes it, and a program that installs nothing ends exactly as it did. An even address, zero included, is a handler, as in EASy68K.
- **The frames and the program counters are the 68000's** (ADR 0007), through one frame builder, `take_exception`, which the 68010 and the 68020 will extend with their format words (ADR 0011):
    - groups 1 and 2 push the status register and the program counter, 6 bytes; the address error pushes the group 0 frame, 14 bytes: the special status word, the access address, the instruction register, the status register and the program counter; *(amended with C7: so does the bus error, its status word the 68000's, R/W as the access was, I/N clear and the function code of the real mode, where EASy68K always says "write" and supervisor; it stacks the program counter an address error at the same access stacks, and an instruction that could not be fetched its own address;)*
    - an illegal instruction, a privilege violation and the line A and F words stack the instruction's own address, and `trap`, `trapv`, `chk` and a division by zero the next instruction's; an address error stacks what MAME's microcode stacks, and a jump to an odd address faults in the jump's own prefetch, as the suite has it for about 7,400 of its tests;
    - entry sets S and clears T, so A7 becomes the supervisor stack pointer; `rte` pops the six bytes and writes the status register back, which can make A7 the user stack pointer again;
    - trace is T as it was before an instruction, taken after it unless it raised an exception of groups 0 or 1, and pushed on top of the frame of one of group 2, so the trace handler runs first;
    - a fault while the frame is pushed, which an odd supervisor stack pointer raises, is a double fault: the processor halts, `Termination::Halted { cause, vector }`. *(Amended with C7: so is a bus error while the exception is taken, a frame pushed where the memory map refuses it or a vector read from an invalid range. The vector is read in supervisor mode, so a protected vector table serves user mode.)*
- **Supervisor and user mode are enforced.** `move <ea>,sr`, `andi`, `ori` and `eori` to `sr`, `rte`, `stop`, `reset` and `move usp` are privileged and raise a privilege violation in user mode; `move sr,<ea>` is not, on a 68000. `trap #15` is EASy68K's service trap in either mode, always, and costs nothing; the vector 47 rule applies only to a task number none of EASy68K's tasks has. A task EASy68K has that s68k cannot carry out (the printer, the serial ports, the network, the hardware window) stays a refusal that ends the program, with no vector, since no handler could do it.

## Considered options

- **EASy68K's option, off by default**: a program would end at every exception unless it asked, which is what s68k already did, and a program that installs a handler would need one more line to work. The design's reading of the option is that it exists for EASy68K's programs that do not set their vectors, and the odd-vector rule gives those the same end without it.
- **The 68000's double fault for an unset vector**: honest to the hardware, but a program that divides by zero by mistake would end with "Halted: an address error on the address error vector", which says nothing about the division.
- **Ending at an odd vector after pushing the frame**: the frame would be in memory and the stack pointer lowered, which a student reading the registers after the end would have to explain away; reading the vector first leaves the state as the instruction left it, as before.
- **Vector 47 for every unsupported task**: a program could not handle a printer task meaningfully, and the editor's message, which names why a task cannot be done in a browser, would become "vector 47 holds no handler".

## Consequences

- ADR 0005's "a task that cannot be done ends the program, as every runtime error now does" no longer holds for every runtime error: an error with a vector ends the program only when the vector holds no handler. A task that cannot be done still ends it, and a number that is no task goes through vector 47 first.
- ADR 0009's illegal instruction and address error, "both of which end the program until exceptions are taken", are taken.
- `Termination::Exception` carries `{ cause, vector }` where it carried the cause alone, and `Termination::Halted { cause, vector }` is new, with the status `TerminatedWithException`. The new causes are `PrivilegeViolation`, `Trace`, `LineA(word)`, `LineF(word)` and `UnhandledTrap { vector }`; `AddressError` carries the access, `Read`, `Write` or `Program`, and the full 32-bit address the 68000 stacks. `Unimplemented` is left to `stop` and `reset`.
- The mutations gain `WriteStackPointers`, `PushException { vector, from, handler }` and `PopException`, and the call stack an exception frame per exception taken, `kind: 'exception'` with its `vector`, which `rte` takes off. Undo takes back an exception, an `rte`, a swap of the stacks and a halt.
- The Assembler assembles `rte`, `move usp,An`, `move An,usp` and `trap #0` to `#14`. The diagnostic `unimplemented_addressing_mode`, whose last Operand was `usp`, is gone; `usp` is an Addressing mode `move` alone takes.
- The conformance suite's exception tests are checked: every skip that waited for milestone C6 is gone, and the whole suite runs 312,340 tests with none failing.
- The exception checks are off the run loop's fast path: an error already left the instruction by its error path, and the one test added is T, a byte already in hand. The benchmark of `ts-lib/test/bench.mjs` measures the same throughput as before, within its noise.
