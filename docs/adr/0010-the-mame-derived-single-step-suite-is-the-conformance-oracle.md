# The MAME-derived single-step suite is the conformance oracle

s68k had no oracle for what an instruction does. Its flags were written from EASy68K's help pages and checked by tests written from the same pages, so a misreading survived both, and an undefined flag or an edge of a shift was whatever the code happened to do. A real 68000 behind the M68K Target (the asm-editor's `docs/design/m68k-machine.md`, decision 34, confirmed by the owner) needs one answer, and its research (`docs/research/m68k-verification-references.md` §1 there) compared the two suites of single-instruction tests. We decided four things.

- **SingleStepTests/m68000 is the oracle.** It is generated from MAME's microcoded 68000, which runs the processor's own microcode; it is MIT, so a subset can be committed; it has 317,500 tests, 2,500 for each of 127 instruction files, starting in user mode or supervisor mode, with trace set or not, and with line A, line F and `stop` among them; and it records every register, the RAM, the bus cycles and the length in cycles. A test that disagrees with it is a bug of s68k's, unless the skip list says why.
- **Tom Harte's set is at most a local second opinion.** It has no licence, so none of it can be committed, and it has known-wrong data: X and C of every `asr` by the size or more, and N and Z of a `divu` that overflows. Nothing in this repository reads it.
- **The harness is behind the `conformance` cargo feature**, and the crate's tests have it without the feature. It holds `Interpreter::from_state`, which makes an Interpreter from a test's state; `Interpreter::from_image` and `Program::from_image`, which load a raw image; the reader of the suite's binary format; the runner, which sets the state, runs one instruction and compares the final registers, SR, program counter and RAM, and checks that nothing else was written; and the skip list. A subset of 50 tests per file, the first that raise no address error, is committed in `tests/m68000/` with the suite's licence and runs in every `cargo test`. The whole suite is fetched at a pinned commit by `scripts/fetch-m68000-tests.sh` and runs with `cargo test --release --features conformance conformance:: -- --ignored`, weekly in CI.
- **Everything not checked is in one skip list, with a reason per line** (`src/conformance/skips.rs`). A skip that waits for a milestone of the machine names it, so that milestone deletes its lines: until C6 every test that takes an exception, raises an address error, changes S or touches the other stack pointer, and `rte`, `move usp`, `trap` and line A and F; until C8 `stop` and `reset`; until C9 the length in cycles, behind one switch. `trap #15` is skipped for good, as it is EASy68K's service trap and not vector 47. The suite's own documented errata are relaxations, one line each with its source: trace is never taken from a test's state, since the suite records the state before the trace exception; memory starts as zeros, which `move.b` and `movep` need; the BCD instructions' undefined N and V are not compared; and the length of `tas` and `trapv` is not trusted, as the suite's README says.

Musashi's sixty self-checking 68000 programs (MIT, committed in `tests/musashi/mc68000/` with its notice) run as a second check, each to the verdict it writes, through watched memory.

## Considered options

- **Tom Harte's set as the oracle**, the better known one: generated by an emulator its author calls flawed, unlicensed, and wrong where we would most need it.
- **Hand-written tests only**, as before: they check what the author believed, which is where the bugs were.
- **Musashi as a differential oracle**, running both side by side: Musashi is an interpretation of the manual too, with its own errata (it leaves N and Z alone on a division overflow), and needs a C toolchain in the tests. It is kept for the dialects, which no suite covers (the plan's `musashi` feature, batch 4).
- **The whole suite committed**, 140 MB: too big for the repository, and the subset finds the same families of bugs in seconds.

## Consequences

- The conformance work of milestone C5 fixed what the suite found in the instruction semantics; each fix has a unit test made from the failing test's data, and a dated note in `tests/corpus/README.md` when a corpus fixture moved.
- An instruction whose result s68k chooses to differ on is a skip marked `Never`, with the reason, and not a silently wrong test.
- Milestones C6, C8 and C9 turn their parts of the suite on by deleting lines of the skip list; a test that then fails is theirs to fix.
